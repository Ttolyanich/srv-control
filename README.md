# 🖥️ SRV-Control Infrastructure & Quota Billing

[![Stack](https://img.shields.io/badge/python-3.10%2B-blue.svg?style=for-the-badge&logo=python)](https://www.python.org/)
[![Framework](https://img.shields.io/badge/Flask-3.0%2B-lightgrey.svg?style=for-the-badge&logo=flask)](https://flask.palletsprojects.com/)
[![Database](https://img.shields.io/badge/SQLite-3-blue.svg?style=for-the-badge&logo=sqlite)](https://www.sqlite.org/)

Легковесная веб-панель управления и финансового учета ИТ-инфраструктуры. Предназначена для мониторинга кластеров Proxmox VE (потребление CPU, RAM, дисков), учета квот бэкап-хранилищ (парсинг `repquota` по SSH) и автоматического биллинга ресурсов клиентов с гибкой тарификацией и ручными ценниками.

---

## ⚡ Основные возможности

* **Мониторинг вычислений (Proxmox VE):** Многопоточная синхронизация с кластерами PVE через API, расчет утилизации CPU, RAM, SSD/HDD по нодам, LXC-контейнерам и виртуальным машинам (с автоматическим исключением шаблонов `template` и сохранением привязок/ценников при миграции ВМ между нодами кластера по `VMID`).
* **Учет дисковых квот (Бэкап-серверы):** Подключение к бэкап-серверам по SSH (пароль или приватные ключи `RSA`, `Ed25519`, `ECDSA`, `DSS`) с парсингом `repquota` и мониторингом свободного места разделов.
* **Биллинг, отчетность и экспорт:**
  * Автоматический расчет стоимости по глобальным или индивидуальным серверным тарифам (за ядро, ГБ RAM, ГБ диска, ГБ бэкапа) с поддержкой ручной фиксации цен (overrides) и живым предпросмотром выручки.
  * Выгрузка полной детализации биллинга в **CSV (UTF-8 BOM для Excel)** и специальная официальная печатная форма отчета по компаниям (**A4 альбомная**).
* **Ролевая модель и Active Directory (LDAP):**
  * Роли Администратора (`admin`), Финансиста (`financier` — просмотр ресурсов, управление тарифами и экспорт отчетов) и Пользователя (`user`).
  * Вход по корпоративной почте (`mail` / `userPrincipalName`) или доменному логину через Active Directory с сохранением резервных локальных учетных записей в БД.
* **Группировка ресурсов и UX:** Объединение ВМ и квот под клиентов с автодополнением компаний (`datalist`), быстрый поиск и расчет долей физических ресурсов хостов.
* **Безопасность:** Шифрование паролей/токенов доступа (`Fernet`) с бесшовной миграцией ключей, защита от брутфорса через общую таблицу SQLite (для всех воркеров Gunicorn), `ProxyFix` и защита от XSS/инъекций.

## ⚙️ Конфигурация окружения (`.env`)

Создайте файл `.env` на основе примера `.env.example`:

| Переменная | Описание | Значение по умолчанию |
| :--- | :--- | :---: |
| `SECRET_KEY` | Секретный ключ подписи Flask сессий | *Автогенерация в `instance/.secret_key`* |
| `FERNET_KEY` | Ключ шифрования PVE/SSH паролей в БД (`Fernet.generate_key()`) | *Генерируется на базе SECRET_KEY (рекомендуется задать явно)* |
| `SYNC_API_TOKEN` | Токен доступа к `/api/sync/*` для cron/скриптов | *Автогенерация в `instance/sync_token`* |
| `DATABASE_URI` | Подключение к БД | `sqlite:///srv_control.db` |
| `BIND_HOST` | Хост для запуска веб-сервера | `0.0.0.0` |
| `BIND_PORT` | Порт для запуска веб-сервера | `5002` |
| `FLASK_DEBUG` | Режим разработки (1) или продакшна (0) | `0` |
| `LDAP_ENABLED` | Включить авторизацию через Active Directory (`true`/`false`) | `false` |
| `LDAP_SERVER` | Адрес контроллера домена (`ldap://10.11.4.254` или `ldaps://...`) | — |
| `LDAP_DOMAIN` | Домен Active Directory (например, `corp.local`) | — |
| `LDAP_BASE_DN` | Базовый DN для поиска (например, `DC=corp,DC=local`) | — |
| `LDAP_BIND_USER` | Сервисная учетка для поиска по атрибуту `mail` (опционально) | — |
| `LDAP_BIND_PASSWORD` | Пароль сервисной учетки | — |
| `LDAP_REQUIRED_GROUP` | CN или DN группы AD, членство в которой обязательно для входа | — |
| `LDAP_ADMIN_GROUP` | CN или DN группы AD для автоматической выдачи роли `admin` | — |
| `LDAP_FINANCIER_GROUP` | CN или DN группы AD для автоматической выдачи роли `financier` | — |
| `LDAP_ADMIN_USERS` | Список email/логинов через запятую для роли `admin` | — |
| `LDAP_NESTED_GROUPS` | Проверять вложенные группы AD (`1.2.840.113556.1.4.1941`) | `true` |

### 🔐 Как работает авторизация через Active Directory (LDAP)

1. **Два режима подключения к AD:**
   * **Search-then-Bind (рекомендуемый):** если заданы `LDAP_BIND_USER` и `LDAP_BIND_PASSWORD`, приложение сначала ищет сотрудника в `LDAP_BASE_DN` по `mail`, `userPrincipalName` или `sAMAccountName`, а затем проверяет его пароль. Это позволяет входить по любому почтовому алиасу (`user@company.ru`), даже если внутренний домен называется иначе (`corp.local`).
   * **Direct Bind:** если сервисная учетка не указана, приложение напрямую авторизуется на контроллере домена под введенным `user@domain` или `DOMAIN\username` и подтягивает ФИО/почту из профиля AD.
2. **Управление правами и ролями:**
   * При первом входе AD-пользователя создается профиль в локальной БД с источником `Active Directory`.
   * Администратор может в любой момент изменить роль сотрудника (`admin`, `financier`, `user`) или заранее добавить AD-пользователя по email без пароля в разделе **Настройки → Пользователи** (`/admin/users`).
   * Локальные пользователи (например, встроенный `admin`) продолжают работать независимо от доступности контроллера домена.

> **Доступ к API синхронизации.** Эндпоинты `/api/sync/<id>` и `/api/sync/all` больше не доверяют запросам с `127.0.0.1` (за reverse-proxy так выглядят все запросы). Штатная автосинхронизация работает через встроенный планировщик внутри приложения и в этих эндпоинтах не нуждается. Из веб-интерфейса под учеткой admin/financier всё работает как раньше. Если когда-нибудь понадобится дернуть синхронизацию внешним скриптом — передавайте токен: `curl -X POST -H "X-Sync-Token: $(cat instance/sync_token)" http://127.0.0.1:5002/api/sync/all`.

## 🚀 Варианты развертывания

### Вариант 1. Запуск через Docker Compose (Рекомендуемый)

1. **Клонирование проекта:**
   ```bash
   git clone https://github.com/Ttolyanich/srv-control.git /opt/srv-control
   cd /opt/srv-control
   ```
2. **Создание и заполнение `.env`:**
   ```bash
   cp .env.example .env
   nano .env
   ```
3. **Запуск контейнера (образ автоматически собирается в GitHub Container Registry):**
   ```bash
   docker compose pull
   docker compose up -d
   ```
   Панель будет доступна на порту `5002` (логин по умолчанию `admin` / пароль `admin123`).

### Вариант 2. Нативный запуск (через Virtualenv)

1. Установите зависимости и подготовьте окружение:
   ```bash
   python3 -m venv venv
   source venv/bin/activate
   pip install -r requirements.txt
   ```
2. Запустите Flask-сервер:
   ```bash
   python3 app.py
   ```
